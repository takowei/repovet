# repovet

Developer trust check for GitHub repos before you depend on them.

**English** | [繁體中文](#繁體中文)

## English

The question behind this tool comes up in a lot of my other work, too: a
trading signal, an agent's benchmark score, a GitHub repo you're about to add
as a dependency — how do you know a result is as good as it looks before you
commit to it. Here that question is applied to open-source dependency
selection instead of taking a star count or a README's word for it.

`repovet` runs a small set of public, re-runnable checks against a GitHub
repo and reports 0-100 scores **with evidence for every sub-score** — no
opaque single number, no LLM in the scoring path. Ships four signals now:
**S2** (zombie maintenance, M0), **S1** (anomalous star pattern, M1), **S3**
(hallucinated dependency / slopsquatting, M2), **S4** (AI-slop feature
hints, v0, M3) — plus `--reply`, a one-command pasteable summary for GitHub
issues / HN / Reddit, in English or Traditional Chinese
(`--lang en|zh`, evidence is native in both). See
`../research/repovet-mvp-spec-2026-07.md` for the full product spec.

None of these four signals is a first: S1's approach is adapted from CMU/NCSU's
"Six Million (Suspected) Fake Stars" research (arXiv:2412.13459) and its
[StarScout](https://github.com/hehao98/StarScout) tool; S3's slopsquatting
concept has prior art in tools like
[slopquat](https://github.com/matteocargnelutti/slopquat); S4 sits in the
newly-emerging "AI-slop linter" category and, by its own honest self-report
below, has weak-to-no discriminating power in v0. What `repovet` adds is
running all four in one command against one repo, instead of assembling four
separate tools yourself.

**Live leaderboard**: <https://takowei.github.io/repovet/> — daily-scanned
trust scores for popular repos, generated by this CLI.

### Install / run

```bash
cd repovet
pip install -e .
export GITHUB_TOKEN=...   # required for S1 (GraphQL has no anonymous tier)
                          # optional for S2 (60 req/hr anonymous vs 5000 req/hr)
repovet gh:psf/requests
repovet gh:psf/requests --json
repovet gh:psf/requests --lang zh                 # same checks, Traditional Chinese evidence
repovet gh:psf/requests --reply                    # pasteable English summary (S1/S2/S3 only)
repovet gh:psf/requests --reply --lang zh          # pasteable Traditional Chinese summary
repovet gh:psf/requests --reply --include-s4       # also include S4's experimental hints
repovet --batch targets.txt --json                 # one target per line, '#' comments allowed
```

`--lang` is a global flag (default `en`): it controls the language of every
signal's evidence text, not just `--reply`'s wrapper copy. Two more flags
tune S2's sampling: `--issue-sample N` (default 15, how many recent
issues/PRs to sample) and `--commit-days N` (commit-cadence lookback window).

Without an install, you can also run it as `PYTHONPATH=src python3 -m repovet gh:owner/repo`.

### Use as a Claude Code / agent skill

`skills/repovet/SKILL.md` packages this CLI as an agent skill: install it and
your coding agent will vet any pasted GitHub URL on request ("is this repo
trustworthy?") and report the scores with evidence.

```bash
mkdir -p ~/.claude/skills/repovet
curl -fsSL https://raw.githubusercontent.com/takowei/repovet/main/skills/repovet/SKILL.md \
  -o ~/.claude/skills/repovet/SKILL.md
```

Without `GITHUB_TOKEN`, S2 still runs (anonymous REST) but S1 is skipped
entirely — `signals.s1.status == "skipped"` in `--json`, clearly marked in
the table view too.

**Gotcha**: `repovet` reads `GITHUB_TOKEN` from the process environment, not
from any file. If you keep your token in a secrets file and `source` it into
your shell, that alone does **not** make it visible to `repovet` (or any
other subprocess) unless the variable is actually exported — sourcing a
file just sets a shell variable. If `repovet` warns "no GITHUB_TOKEN set"
right after you sourced your secrets file, run `export GITHUB_TOKEN` (no
value needed if it's already set in your shell) before invoking `repovet`.

### Exit codes (pipeline-friendly by design)

| Code | Meaning                                                                  |
| ---- | ------------------------------------------------------------------------ |
| 0    | Completed normally                                                       |
| 2    | Input error (bad target, repo not found, bad batch file)                 |
| 3    | API/network failure (rate limit, connection error, unexpected API error) |

In `--batch` mode the exit code reflects the _worst_ status across all
targets (3 beats 2 beats 0). The top-level exit code is governed by **S2
only** — if S2 succeeds but S1 fails or is skipped, the record is still
`"status": "ok"` overall; S1's own outcome is visible at
`signals.s1.status` for anything reading the JSON that cares.

### S2 — zombie maintenance scoring (formula `s2.v2`)

**Philosophy**: a mature, feature-complete project can have a stale last
commit/release and still be perfectly healthy — as long as issues still get
a response and _someone_ still shows up occasionally. Raw commit/release
cadence is therefore only 20% of the score; issue responsiveness (30%) and
recent maintainer activity (25%) do the real work of telling "stable" apart
from "abandoned". Bus factor (15%) is a standing risk factor, not a verdict.

**v1 → v2 change**: issue and PR responsiveness are now scored (and
weighted) separately, instead of one blended "issue/PR" score. On popular
repos (e.g. `psf/requests`) the combined sample was dominated by low-effort
driveby PRs that maintainers correctly ignore, which dragged the score down
even on a genuinely healthy repo — found during the M0 demo, fixed before
this could mislead anyone. Real user-filed issues keep the larger weight
(30%); PR non-response is weaker/more ambiguous and gets a smaller one (10%).

Five sub-scores, each 0-100, weighted into an overall score:

| Sub-score                  | Weight | What it measures                                                                                                                                                 |
| -------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| commit/release cadence     | 20%    | Days since the more recent of last commit / last release, banded 100→10 (never hits 0 — silence alone isn't proof of death)                                      |
| issue responsiveness       | 30%    | Of the most recent N (default 15) issues+PRs _old enough to have had a fair chance at a response_ (≥2 days), filtered to plain issues: response fraction + speed |
| PR responsiveness          | 10%    | Same, filtered to PRs only. Evidence explicitly flags this may include unreviewed/low-quality driveby PRs — non-response here is a weaker signal                 |
| bus factor                 | 15%    | Commits in the last year, min. number of contributors needed to cover ≥50% of them                                                                               |
| maintainer 90-day activity | 25%    | Days since the most recent of {commit, release, any issue/PR first response} — a genuine "is anyone touching this at all" proxy                                  |

`pattern` label (driven off **issue** responsiveness specifically, not the
old PR-diluted blend): `healthy` / `stable-low-frequency` ("finished
software", not abandoned) / `anomalous-stalled` (the actual zombie signal) /
`mixed`.

### S1 — anomalous star pattern scoring (formula `s1.v1`)

**Method basis**: CMU/NCSU "Six Million (Suspected) Fake Stars on GitHub"
(arXiv:2412.13459, ICSE'26) and its [StarScout](https://github.com/hehao98/StarScout)
tool. StarScout runs at GitHub-Archive scale with two heuristics: a
low-activity heuristic (throwaway accounts) and a CopyCatch lockstep
heuristic (dense bipartite cores of accounts starring many repos together
across _all of GitHub_). A single-repo CLI query can't replicate the
cross-repo lockstep heuristic (it needs a full star-event graph), so S1
adapts the spirit of both to what one live GraphQL query can see:

| Sub-score                 | Weight | What it measures                                                                                                          |
| ------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------- |
| star-burst timing         | 25%    | Max fraction of the sample inside any single 48h window — is the timeline itself anomalously bursty                       |
| account quality           | 40%    | Fraction of sampled starrers matching ≥2 of {zero owned repos, zero followers, account created within 7 days of the star} |
| burst/account correlation | 35%    | Are suspicious accounts concentrated _inside_ the burst window specifically, vs the rest of the sample (the baseline)?    |

Score direction matches S2: 100 = no evidence of anomalous star activity, 0
= strong evidence. Language is always "anomalous star pattern", never
"fraud"/"fake" as a factual claim about the repo owner.

**Why burst/account correlation is weighted highest**: a beginner-friendly
tutorial repo can genuinely attract many brand-new GitHub accounts (their
first star ever) without any fraud — but real new-user adoption trickles in
over time, it doesn't burst. A Hacker-News-style organic viral spike _does_
burst, but with real, diverse accounts. A bought campaign does both at
once: burst timing _and_ throwaway accounts, concentrated together. That
co-occurrence is the most specific signal we have.

**Sampling strategy** (always stated in the evidence, never silent):

- `stargazerCount <= 2000`: full scan, no blind spots.
- above that: stratified sample of the most recent ~300 stars (DESC) +
  earliest ~200 (ASC). Catches "recent/ongoing campaign" and "inflated at
  launch" patterns. **A campaign buried in the middle of a large repo's
  star history will be missed** — this is a real, disclosed blind spot, not
  hidden in the score.

#### Calibration (small sample, directional only — see caveat below)

Positives from StarScout's own published Jan-2025 low-activity results
([gist](https://gist.github.com/heathdutton/e09693d7f8b18df8df3061a57105b112),
derived from the ICSE'26 paper's tool). Most of the originally-flagged repos
in that dataset have since been removed by GitHub (spam takedowns); these
three still existed and were small enough for a **full scan** (no sampling
blind spot):

| Repo                            | Published fake-star % | repovet S1 result               | Verdict       |
| ------------------------------- | --------------------- | ------------------------------- | ------------- |
| `sidetrip-ai/ici-core`          | 82%                   | 28/100 `anomalous-star-pattern` | **hit**       |
| `pEgaSuShoOFtR/APP-HyperDefi`   | 85%                   | 40/100 `anomalous-star-pattern` | **hit**       |
| `AceDataCloud/Nexior`           | 81%                   | 90/100 `clean`                  | **miss (FN)** |
| `psf/requests` (known healthy)  | n/a                   | 80/100 `organic-burst`          | correct (TN)  |
| `pallets/flask` (known healthy) | n/a                   | 80/100 `organic-burst`          | correct (TN)  |

**n=5 (3 positive, 2 negative): precision = 2/2 = 100%, recall = 2/3 ≈ 67%.**
This is far too small a sample to claim a real precision/recall number —
treat it as directional evidence the method works, not a validated
statistic. Every other originally-flagged repo we tried to use for
calibration had already been deleted by GitHub, which is itself informative
(GitHub's own abuse detection got there first) but shrank our usable set.

**Why the miss happened (found during calibration, not hidden)**: we only
see a starrer's _current_ account profile (current repo count, current
follower count), not their state at the time they starred. `Nexior`'s
campaign was mid-2024; those accounts may have built up real activity since
then and no longer look like throwaways today. `ici-core`'s campaign was
March-May 2025, recent enough that the accounts still look exactly like what
they were. **S1 is structurally weaker at detecting older campaigns** — this
is the single biggest known limitation of the current formula.

#### Known limitations

1. **Current-state-only account features** (see miss above) — the biggest
   one. Detection strength decays as a campaign ages.
2. **Stratified sampling blind spot** on large repos (see sampling strategy
   above) — a mid-history campaign on a 50k+ star repo would be invisible
   to the default sample.
3. **Burst/account correlation weakens when almost the whole sample is
   fake**, not just a narrow window (no clean "baseline" left to compare
   against). Fixed with a floor rule (`account quality < 20` alone is
   enough to call it anomalous, provided there's _some_ timing
   concentration — see `_classify_pattern` in `star_scoring.py`), but it's
   a real edge case worth knowing about.
4. **No cross-repo lockstep detection.** The paper's strongest signal (the
   same group of accounts coordinating across _many_ repos) needs a
   full star-event graph we don't have in a single-repo query.

### S3 — hallucinated dependency scoring (formula `s3.v1`)

**What it checks**: for every dependency declared in a supported manifest,
does it actually exist in its registry? A dependency that doesn't exist at
all is the single most severe, most directly verifiable signal repovet has
— it's the literal slopsquatting attack surface (an LLM hallucinates an
import name, someone registers that exact name with malware, the next
`pip install`/`npm install` grabs it). The concept has prior art in tools
like [slopquat](https://github.com/matteocargnelutti/slopquat); S3 folds the
same idea into repovet's single-command scan instead of a standalone check.

**Supported ecosystems (MVP, explicitly limited)**: Python
(`pyproject.toml`'s PEP 621 `dependencies`/`optional-dependencies` +
`requirements*.txt`) and JS (`package.json`'s `dependencies`/
`devDependencies`). Any other ecosystem (Go, Rust, Ruby, ...) reports S3 as
`skipped: no supported dependency manifest found` rather than guessing.

| Sub-score            | Weight | What it measures                                                                                                                                                                                    |
| -------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| dependency existence | 55%    | Fraction of declared dependencies that exist in their registry. **Capped hard** at 40/100 if even one is missing — a hallucinated import shouldn't be diluted away by a big healthy dependency tree |
| typosquat risk       | 30%    | Fraction of existing dependencies that are name-adjacent (edit distance ≤2) to a well-known package **and** themselves look fresh/low-signal (age <30 days or, npm only, <100 weekly downloads)     |
| package maturity     | 15%    | Informational: fraction of dependencies younger than 30 days. Being young isn't inherently bad, so this is the lightest-weighted sub-score                                                          |

**Typosquat detection always defers to registry data over string
similarity.** A real, long-established package that happens to be
name-adjacent to a popular one (e.g. npm's `request`, a genuine 2011-era
package) must never be flagged just because an edit-distance check fired —
only a name-adjacent package that is _also_ young or low-download gets
flagged. Verified with a unit test using exactly this case.

**Known limitations**:

- The "well-known package" list is a curated ~60-name-per-ecosystem
  allowlist (`popular_packages.py`), not a live top-N-by-downloads feed —
  squatting against a popular name that isn't on this list won't be caught.
- **PyPI packages carry no download-count signal at all.** pypistats.org
  (the obvious source) 429s on back-to-back requests — verified
  empirically, unsuitable for checking N dependencies in one run. This is
  disclosed via a warning in the output, not silently treated as zero.
- `requirements.txt` `-r other.txt` includes are not followed recursively.

#### S3 demo

Against a real healthy repo (`psf/requests`, `--json` excerpt):

```
S3 hallucinated dependency: 100/100 [clean]
  dependency existence   100/100  all 12 dependencies exist in their registry
  typosquat risk         100/100  12 existing dependencies checked, no typosquat-like names found
  package maturity       100/100  0/12 dependencies with known age are <30 days old
  manifests: pyproject.toml, requirements-dev.txt
  warning: PyPI packages carry no download-count signal (pypistats API too rate-limited)
```

Against a self-made fixture (3 real deps checked live against PyPI +
1 confirmed-nonexistent name + 1 synthetic typosquat-style entry — see
"why synthetic" note below):

```
overall: 40/100  pattern: hallucinated-dependency  formula: s3.v1
  dependency existence   40/100  1/5 dependencies don't exist in their registry: zzz-repovet-hallucinated-fixture-test-9f3k2
  typosquat risk         25/100  1/4 existing dependencies look like typosquat candidates: reqeusts (close to requests, 3 days old)
  package maturity       75/100  1/4 dependencies with known age are <30 days old
```

_Why one entry is synthetic_: finding a **real, currently-existing,
young/low-download package name that's also a live typosquat attempt**
would mean deliberately hunting for and then naming an actual attack
package in a public demo — not something we're going to do. The
nonexistent-package half of the fixture (the more severe, heavier-weighted
signal) is 100% real: `zzz-repovet-hallucinated-fixture-test-9f3k2` was
verified live against the PyPI JSON API (HTTP 404) before use. The
typosquat half uses a hand-constructed `PackageInfo` fed straight into
`compute_s3` — the scoring logic itself doesn't care whether the data came
from a live lookup or not, and this is disclosed here rather than implied
to be a live finding.

### S4 — AI-slop feature hints (v0, `formula "s4.v0"`)

**Deliberately not a score.** Unlike S1/S2/S3, S4 has no 0-100 number and
no `pattern` verdict — per spec, it's the highest false-positive-risk
signal in the tool (README template similarity, commit-message
homogeneity, and scaffolding similarity are all things completely
legitimate, human-run projects exhibit too). v0 emits `signals.s4.hints[]`
only: each hint is an observation + a raw number + an explicit "this also
happens in normal repos" disclaimer. No aggregation, no verdict. S4 sits in
the newly-emerging "AI-slop linter" category of tools; unlike S1/S3 it
isn't adapted from a specific prior paper or tool.

| Hint                             | What it measures                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| readme badge density             | Count of shields.io/badge-style images in the README                                                                                                   |
| README emoji-header density      | Fraction of `#`-headers (outside code fences) containing an emoji                                                                                      |
| README boilerplate phrase hits   | Count of matches against a curated list of common AI-generated-README phrases                                                                          |
| commit message length uniformity | Coefficient of variation of the last 30 commit messages' lengths (lower = more uniform); skipped if n<8                                                |
| repo scaffolding completeness    | Count of common professional-project markers present (LICENSE, CONTRIBUTING.md, CODE_OF_CONDUCT.md, SECURITY.md, issue templates, `.github/workflows`) |

`--reply` **excludes S4 by default** — the riskiest-to-misfire signal
doesn't belong in a public post unless asked for. Pass `--include-s4` to
add an "AI-slop hints (experimental)" section to the reply.

#### S4 demo — honest result: weak-to-no discriminating power on this pair

Per the spec's own instruction, a v0 signal with near-zero discriminating
power is an acceptable, honestly-reported outcome — not something to force
better by cherry-picking a flattering comparison. Ran against a normal repo
(`psf/requests`) and a suspected-AI-slop repo pulled from S1's calibration
set (`sidetrip-ai/ici-core`, a small "AI assistant" project):

| Hint                             | psf/requests (normal) | ici-core (suspected AI-slop)     | Discriminates?                                                                   |
| -------------------------------- | --------------------- | -------------------------------- | -------------------------------------------------------------------------------- |
| readme badge density             | 5                     | 0                                | **No — wrong direction.** Badges usually mean real CI/PyPI integration, not slop |
| README emoji-header density      | 0/4 (0%)              | 0/26 (0%)                        | No — both zero                                                                   |
| README boilerplate phrase hits   | 0/9                   | 1/9 ("we welcome contributions") | Weak, expected direction, thin evidence                                          |
| commit message length uniformity | CV 0.42               | CV 0.24                          | Weak-to-moderate, expected direction (more uniform)                              |
| repo scaffolding completeness    | 3 markers             | 3 markers                        | No — tied                                                                        |

**Bottom line**: on this pair, only one hint (commit-message uniformity)
points weakly in the expected direction; one (badge density) points the
_opposite_ way of a naive reading (which is exactly why its disclaimer
exists); the rest don't discriminate at all. This matches the honest
framing repovet commits to everywhere else: v0 AI-slop hints are things
for a human to glance at, not a detector. No feature was retuned or
swapped to make this look better after the fact.

A real bug was found and fixed during this demo, worth naming: naive
`#`-line counting for headers was inflating ici-core's header count to 60
by counting bash comments inside ` ``` `-fenced setup snippets as if they
were markdown headers. Fixed by skipping fenced-code-block lines before
counting (`_lines_outside_code_fences` in `ai_slop_hints.py`); a regression
test covers it.

### `--reply`

`repovet gh:owner/repo --reply` renders a neutral, evidence-first summary
meant to be pasted as-is into a GitHub issue, Hacker News, or Reddit thread
answering "is this repo legit?" — S1/S2/S3 scores, the 3-5 lowest-scoring
(most decision-relevant) sub-scores as evidence, a one-line
method/limitations statement, and a tool signature. Never uses accusatory
language ("anomalous pattern", never "fraud"/"fake") — that discipline
lives in the underlying evidence strings already; `--reply` only assembles
what's already there, it doesn't generate new claims. `--reply --lang zh`
renders the same content in Traditional Chinese — both are fully
native today (see M2.5 below). S4 is excluded unless `--include-s4` is
passed.

#### M2.5: evidence is now English-native (resolved scope gap)

M0-M2 authored all evidence prose in Chinese; the English `--reply`
therefore embedded Chinese sentences verbatim, which the coordinator
correctly flagged as a hard blocker before any public posting. Fixed:
every `score_*` function in `scoring.py`/`star_scoring.py`/
`dependency_scoring.py`/`ai_slop_hints.py` now takes a `lang: "en" | "zh"`
parameter (default `"en"`) and builds both language strings **co-located
at the same construction site** (not in separate files), so a future
change to the underlying facts can't update one language and silently
forget the other. `SubScore.name`/`Hint.name` and `pattern` stay
English-only regardless of `lang` — they're stable identifiers other code
and tests match against, not prose to localize. Formula versions were not
bumped (text-only change, no logic/weights/thresholds touched); all
pre-existing tests kept passing unchanged, plus one new lang-parity test
per module (same scores/patterns across languages, only the prose differs).

One small residual gap, disclosed rather than silently left: S1's
top-level `sampling_note` field describing the star-sampling strategy is
still English-only regardless of `--lang` — it's a collector-level
metadata field, not one of the per-sub-score evidence strings the
coordinator's ask was about, but it will look slightly inconsistent in a
`--lang zh` run. Not fixed here; flagging it rather than letting it look
accidental.

### Automation / bot

repovet can run as a GitHub Action instead of a manual CLI invocation, in
two deliberately **opt-in** shapes — there is no path that scans or
comments on a repo whose maintainer didn't ask for it.

#### 1. `/repovet-check` comment bot (this repo)

Comment `/repovet-check gh:owner/repo` on any issue in
[`takowei/repovet`](https://github.com/takowei/repovet) and a bot replies
in that same issue with a `--reply`-style summary of `owner/repo`. The
reply always goes back to the issue where the command was typed — running
a check on `owner/repo` never causes a comment to be posted _to_
`owner/repo`. Implemented by
`.github/workflows/issue-comment-bot.yml` → `src/repovet/bot_cli.py` →
`src/repovet/bot.py`, using the Action's built-in `GITHUB_TOKEN` (scoped
to this repo only — no personal PAT involved, nothing for you to manage).

#### 2. Reusable watchlist workflow (your repo, your opt-in)

If you want periodic repovet checks on repos/dependencies _you_ care
about, copy a small workflow into **your own repo** that calls
`takowei/repovet`'s reusable `workflow_call` workflow on a watchlist file
you maintain. It scans on your schedule and posts the report as a new
issue in **your own repo** — again, using your repo's own Action-scoped
token, and it never reaches into any repo other than the ones you listed.
Full copy-paste setup: [`docs/reusable-watchlist-workflow.md`](docs/reusable-watchlist-workflow.md).

#### Why not "auto-comment on any repo repovet scans"?

Because that's a spam bot and gets you rate-limited/blocked — GitHub is
the only platform with an accepted automated-comment convention
(Snyk/Socket-style), and even there it's opt-in-only. Both mechanisms
above only ever act inside a repo whose own maintainer explicitly invoked
repovet — never a third party's.

### GitHub App / Marketplace (stage 1: free-tier listing)

A third automation shape, on top of the two Action-based ones above: a
**GitHub App** with its own webhook server, aimed at the GitHub
Marketplace. Where the Action bots above run inside GitHub's own runners
with no infrastructure to operate, a Marketplace _App_ (as opposed to a
Marketplace _Action_) requires you to run a persistent webhook endpoint
yourself — GitHub calls out to it on every event, there's no way around
that for App-type listings.

**Why an App and not "just" the Action bot above?** Marketplace listings
for Actions exist too, but the paid-subscription billing plumbing
(`marketplace_purchase` webhook, per-account plan state) is only wired up
for Apps in GitHub's model — so the App route is what stage 2 (paid tiers)
needs, and stage 1 builds on the same skeleton starting free-only.

#### What's implemented

- `src/repovet/app_server.py` — a small stdlib-only (`http.server`, no
  Flask) webhook server. `POST /webhook` verifies the
  `X-Hub-Signature-256` HMAC (`src/repovet/webhook_security.py`, fails
  closed on any missing/invalid signature) before touching the payload.
  `GET /health` for uptime checks.
- `src/repovet/app_auth.py` — signs the App's RS256 JWT and exchanges it
  for a short-lived per-installation access token (`get_installation_token`).
  Tokens are minted fresh per webhook delivery, never cached across requests.
- `src/repovet/app_webhook.py` — event dispatch:
  - `pull_request` (`opened`/`reopened`/`synchronize`): runs a repovet scan
    on the PR's repo and posts the result as a PR comment, reusing the same
    `bot.py`/`reply.py` rendering path as the Action bot.
  - `marketplace_purchase` (`purchased`/`changed`/`pending_change`/
    `cancelled`): keeps `src/repovet/plan_store.py` (local sqlite) in sync
    with GitHub's billing state. **Wired up now even though stage 1 ships
    free-only** — GitHub requires an App to already have ≥100 installations
    before a paid plan can go live, so this stays dormant until that
    threshold is hit, but the code path has to exist first.
  - `installation`, `installation_repositories`, `ping`: acknowledged, no-op.
- `src/repovet/plan_store.py` — sqlite table of `account_login → plan`;
  `get_plan()` is the one place any future feature gating would read from.

#### Running the server

```bash
REPOVET_APP_ID=... \
REPOVET_APP_PRIVATE_KEY="$(cat app-private-key.pem)" \
REPOVET_WEBHOOK_SECRET=... \
python3 -m repovet.app_server   # or: repovet-app-server
```

All three secrets come from the environment only — never a literal file
path in source, never logged. `PORT` (default `8080`) is the only other
env var it reads.

See `docs/github-app-setup.md` for the exact copy-paste checklist (field
values, permission levels, event list) for the manual steps below.

#### Manual steps (GitHub-side, not automatable from this sandbox — Root's hands)

1. Create the GitHub App at github.com/settings/apps/new: name, homepage
   URL, webhook URL (`https://<your-host>/webhook`), webhook secret,
   permissions (`Pull requests: Read & write`, `Contents: Read`,
   `Metadata: Read`), and subscribe to events `pull_request`,
   `marketplace_purchase`, `installation`, `installation_repositories`.
2. Generate a private key for the App (downloads a `.pem`); keep it and
   the webhook secret out of the repo — set them as env vars/secrets on
   wherever the server is deployed, never committed.
3. Deploy `repovet-app-server` somewhere with a stable public HTTPS URL
   (a small VPS behind a reverse proxy, or any container host) — this repo
   does not include deployment/hosting config, only the server itself.
4. List the App on GitHub Marketplace: Marketplace Developer Agreement,
   logo, feature card, screenshots, listing copy, pricing plans page (free
   plan only for stage 1).
5. Submit for review (real person, no published SLA — community reports
   ~2-6 weeks).
6. Once ≥100 installations are reached, add a paid plan on the Marketplace
   listing page — `plan_store`/`app_webhook.py` already handle the
   resulting `marketplace_purchase` events, no code changes needed to flip
   that on.

## 繁體中文

[English](#repovet) | **繁體中文**

在加一個 GitHub repo 當依賴、或決定要不要相信一個 repo 之前，你怎麼知道
它看起來的樣子是真的？這個問題在我其他線上也一直出現（一個交易訊號、一個
agent 的評測分數），這裡把同樣的問題套用在開源依賴選擇上，取代單看 star
數或 README 自吹自擂。

`repovet` 對一個 GitHub repo 跑一組公開、可重複執行的檢查，回報 0-100 分
**且每個子分數都附證據**——不是不透明的單一數字，評分邏輯裡也沒有 LLM。
目前上線四個訊號：**S2**（殭屍維護，M0）、**S1**（異常星標模式，M1）、
**S3**（幻覺依賴／slopsquatting，M2）、**S4**（AI-slop 特徵提示，v0，
M3）——外加 `--reply`，一個指令產生可直接貼上 GitHub issue／HN／Reddit 的
摘要文案，支援英文或繁體中文（`--lang en|zh`，兩種語言的證據文字都是原
生撰寫）。完整產品規格見 `../research/repovet-mvp-spec-2026-07.md`。

這四個訊號沒有一個是業界首創：S1 的方法改編自 CMU/NCSU 的「Six Million
(Suspected) Fake Stars」研究（arXiv:2412.13459）與其
[StarScout](https://github.com/hehao98/StarScout) 工具；S3 的 slopsquatting
概念在 [slopquat](https://github.com/matteocargnelutti/slopquat) 這類工具
上已有先例；S4 屬於新興的「AI-slop linter」這類工具，且如下方誠實自評所
示，v0 版本的鑑別力偏弱到幾乎沒有。`repovet` 真正加的價值是：一個指令跑完
這四個訊號，省下自己拼湊四個獨立工具的時間。

**即時排行榜**：<https://takowei.github.io/repovet/> ——由本 CLI 產生、
每日掃描熱門 repo 的信任分數。

### 安裝 / 執行

```bash
cd repovet
pip install -e .
export GITHUB_TOKEN=...   # S1 必須（GraphQL 沒有匿名額度）
                          # S2 選用（匿名 60 次/時 vs 有token 5000 次/時）
repovet gh:psf/requests
repovet gh:psf/requests --json
repovet gh:psf/requests --lang zh                 # 相同檢查，證據改用繁體中文
repovet gh:psf/requests --reply                    # 可直接貼上的英文摘要（僅 S1/S2/S3）
repovet gh:psf/requests --reply --lang zh          # 可直接貼上的繁體中文摘要
repovet gh:psf/requests --reply --include-s4       # 摘要也納入 S4 的實驗性提示
repovet --batch targets.txt --json                 # 一行一個 target，'#' 開頭視為註解
```

`--lang` 是全域旗標（預設 `en`）：控制的是每個訊號證據文字的語言，不只
是 `--reply` 外層文案。另外兩個旗標可調整 S2 的取樣：`--issue-sample N`
（預設 15，取最近幾筆 issue/PR）與 `--commit-days N`（commit 頻率的回看
天數）。

不想安裝的話，也可以用 `PYTHONPATH=src python3 -m repovet gh:owner/repo`
直接執行。

`repovet`。

### 結束代碼（管線友善設計）

| 代碼 | 意義                                                     |
| ---- | -------------------------------------------------------- |
| 0    | 正常完成                                                 |
| 2    | 輸入錯誤（target 格式錯、repo 不存在、batch 檔案錯誤）   |
| 3    | API／網路失敗（rate limit、連線錯誤、非預期的 API 錯誤） |

`--batch` 模式下，結束代碼取所有 target 裡「最糟」的狀態（3 > 2 > 0）。
最上層的結束代碼只由 **S2** 決定——如果 S2 成功但 S1 失敗或被跳過，整筆
紀錄的 `"status"` 依然是 `"ok"`；S1 自己的結果會出現在 `signals.s1.status`，
需要在意的人自己從 JSON 裡讀。

### S2 — 殭屍維護評分（公式 `s2.v2`）

**理念**：一個成熟、功能完整的專案，即使最後一次 commit／release 已經很
久，只要 issue 還有人回、偶爾還有人出現，就依然是健康的。所以原始的
commit/release 頻率只佔 20% 權重；issue 回應度（30%）與最近的維護者活動
（25%）才是真正區分「穩定」與「已棄坑」的關鍵。Bus factor（15%）是一個
常態性風險因子，不是結論。

**v1 → v2 的改變**：issue 與 PR 的回應度現在分開計分（也分開加權），不
再混成一個「issue/PR」分數。在熱門 repo（例如 `psf/requests`）上，混在
一起的樣本會被大量低品質的 driveby PR 拖累分數——即使 repo 其實很健康、
維護者正確地忽略那些 PR。這是在 M0 demo 時發現、在造成誤導前就修好的。
真正的使用者回報 issue 保留較大權重（30%）；PR 沒被回應的訊號較弱、較
含糊，權重較小（10%）。

五個子分數，各 0-100，加權成總分：

| 子分數              | 權重 | 衡量什麼                                                                                                     |
| ------------------- | ---- | ------------------------------------------------------------------------------------------------------------ |
| commit/release 頻率 | 20%  | 距最近一次 commit／release（取較近者）的天數，分級 100→10（永遠不會到 0——沒動靜不等於已死）                  |
| issue 回應度        | 30%  | 最近 N 筆（預設 15）issue+PR 中，「已足夠久、有公平機會被回應」（≥2 天）且過濾為純 issue 的：回應比例 + 速度 |
| PR 回應度           | 10%  | 同上，但過濾為 PR。證據會明確標示這裡可能混有沒被審查的低品質 driveby PR——沒被回應在這裡是較弱的訊號         |
| bus factor          | 15%  | 過去一年的 commit 數，需要多少最少貢獻者才能覆蓋其中 ≥50%                                                    |
| 維護者 90 天活動度  | 25%  | 距 {commit、release、任何 issue/PR 的第一次回應} 中最近一次的天數——「到底還有沒有人在動」的真實代理指標      |

`pattern` 標籤（由 **issue** 回應度單獨驅動，不是舊版被 PR 稀釋的混合值）：
`healthy`／`stable-low-frequency`（「功能已完成」，不是棄坑）／
`anomalous-stalled`（真正的殭屍訊號）／`mixed`。

### S1 — 異常星標模式評分（公式 `s1.v1`）

**方法依據**：CMU/NCSU 的「Six Million (Suspected) Fake Stars on GitHub」
（arXiv:2412.13459，ICSE'26）與其 [StarScout](https://github.com/hehao98/StarScout)
工具。StarScout 在 GitHub Archive 規模上跑兩種啟發式：低活躍度啟發式
（用完即丟的帳號）與 CopyCatch lockstep 啟發式（一群帳號在**全 GitHub
範圍**內一起大量互相加星的密集二部圖核心）。單一 repo 的 CLI 查詢無法複
製跨 repo 的 lockstep 啟發式（需要完整的加星事件圖），所以 S1 把兩者的
精神改編成一次即時 GraphQL 查詢能看到的範圍：

| 子分數                   | 權重 | 衡量什麼                                                                             |
| ------------------------ | ---- | ------------------------------------------------------------------------------------ |
| 星標突發時間點           | 25%  | 樣本中落在任何單一 48 小時窗口內的最大比例——時間軸本身是否異常爆發                   |
| 帳號品質                 | 40%  | 抽樣加星者中符合 ≥2 項的比例：{零個自己的 repo、零追蹤者、帳號在加星前後 7 天內建立} |
| 突發時間點與帳號的相關性 | 35%  | 可疑帳號是否**集中**在爆發窗口內，相對於樣本其餘部分（作為基準）？                   |

分數方向與 S2 一致：100 = 沒有異常星標活動的證據，0 = 有強烈證據。用語
永遠是「異常星標模式」，絕不對 repo 擁有者做「詐騙」／「造假」這種事實
指控。

**為什麼「突發時間點與帳號相關性」權重最高**：一個新手向的教學 repo 可以
在完全沒有造假的情況下，真的吸引很多全新的 GitHub 帳號（他們人生第一次
加星）——但真實的新使用者採用是慢慢滴進來的，不會爆發。Hacker News 式的
有機爆紅**會**爆發，但帳號是真實、多樣的。付費操作的活動會同時做到兩
件事：爆發時間點**和**用完即丟的帳號，而且集中在一起。這種同時出現是我
們手上最具特異性的訊號。

**取樣策略**（一定會寫在證據裡，不會悄悄省略）：

- `stargazerCount <= 2000`：全量掃描，沒有盲區。
- 超過此數：分層取樣，最近約 300 筆星標（由新到舊）+ 最早約 200 筆
  （由舊到新）。可抓到「近期／進行中的操作」與「上線時灌水」兩種模式。
  **埋在一個大 repo 星標歷史中段的操作會被漏掉**——這是一個真實、已揭露
  的盲區，不是藏在分數裡的秘密。

#### 校準（小樣本，僅供方向參考——見下方但書）

正樣本取自 StarScout 自己在 2025 年 1 月公開的低活躍度結果
（[gist](https://gist.github.com/heathdutton/e09693d7f8b18df8df3061a57105b112)，
源自 ICSE'26 論文的工具）。該資料集中大多數原本被標記的 repo 現在都已
被 GitHub 移除（垃圾帳號下架），以下三個當時仍存在、且規模小到可以
**全量掃描**（沒有取樣盲區）：

| Repo                          | 公開的假星比例 | repovet S1 結果                 | 判定          |
| ----------------------------- | -------------- | ------------------------------- | ------------- |
| `sidetrip-ai/ici-core`        | 82%            | 28/100 `anomalous-star-pattern` | **命中**      |
| `pEgaSuShoOFtR/APP-HyperDefi` | 85%            | 40/100 `anomalous-star-pattern` | **命中**      |
| `AceDataCloud/Nexior`         | 81%            | 90/100 `clean`                  | **漏判 (FN)** |
| `psf/requests`（已知健康）    | n/a            | 80/100 `organic-burst`          | 正確判斷 (TN) |
| `pallets/flask`（已知健康）   | n/a            | 80/100 `organic-burst`          | 正確判斷 (TN) |

**n=5（3 正 2 負）：precision = 2/2 = 100%，recall = 2/3 ≈ 67%。**
樣本數太小，不足以宣稱這是真正驗證過的 precision/recall 數字——只能當
成「這個方法有效」的方向性證據，不是統計結論。其他原本被標記的 repo 幾
乎都已經被 GitHub 刪除，這件事本身有參考價值（GitHub 自己的濫用偵測先
一步處理掉了），但也讓我們可用的樣本變少。

**為什麼會漏判（在校準過程中發現、沒有隱瞞）**：我們只能看到加星者
**目前**的帳號狀態（現在的 repo 數、現在的追蹤者數），看不到他們加星
當下的狀態。`Nexior` 的操作是 2024 年中的事；那些帳號可能之後累積了真
實活動，現在已經不像用完即丟的帳號了。`ici-core` 的操作發生在 2025 年
3-5 月，夠近，那些帳號現在看起來還是跟當時一模一樣。**S1 在偵測較舊的
操作活動時結構性地較弱**——這是目前公式已知最大的限制。

#### 已知限制

1. **只看帳號當下狀態的特徵**（見上方漏判案例）——最大的一項。操作活動
   越舊，偵測力越弱。
2. 大型 repo 上的**分層取樣盲區**（見上方取樣策略）——一個 5 萬星以上
   repo 的歷史中段操作，預設取樣看不到。
3. **當幾乎整個樣本都是假的時，突發時間點與帳號的相關性會失效**，不只
   是狹窄窗口的問題（沒有乾淨的「基準」可以比較）。已用一條底線規則
   修正（只要有*某種*時間集中性，`account quality < 20` 本身就足以判
   定為異常——見 `star_scoring.py` 的 `_classify_pattern`），但這仍是
   一個值得知道的真實邊界案例。
4. **不做跨 repo 的 lockstep 偵測。** 論文最強的訊號（同一群帳號在
   **許多** repo 間協同操作）需要完整的加星事件圖，單一 repo 查詢拿不
   到。

### S3 — 幻覺依賴評分（公式 `s3.v1`）

**檢查什麼**：manifest 裡宣告的每一個依賴，是否真的存在於對應的套件註
冊庫？完全不存在的依賴是 repovet 手上最嚴重、也最能直接驗證的訊號——這
就是 slopsquatting 攻擊面本身（LLM 幻覺出一個 import 名稱，有人拿這個
確切名稱註冊惡意套件，下一次 `pip install`／`npm install` 就抓到它）。
這個概念在 [slopquat](https://github.com/matteocargnelutti/slopquat) 這
類工具上已有先例；S3 把同樣的想法折進 repovet 的單指令掃描裡，而不是
做成一個獨立工具。

**支援的生態系（MVP，明確限縮）**：Python（`pyproject.toml` 的 PEP 621
`dependencies`/`optional-dependencies` + `requirements*.txt`）與 JS
（`package.json` 的 `dependencies`/`devDependencies`）。其他生態系（Go、
Rust、Ruby……）S3 一律回報 `skipped: no supported dependency manifest
found`，不會用猜的。

| 子分數       | 權重 | 衡量什麼                                                                                                                  |
| ------------ | ---- | ------------------------------------------------------------------------------------------------------------------------- |
| 依賴存在性   | 55%  | 宣告的依賴中，實際存在於註冊庫的比例。**只要有一個不存在就硬性封頂在 40/100**——一個幻覺 import 不該被一大堆健康依賴稀釋掉 |
| 打字搶注風險 | 30%  | 現存依賴中，名稱與知名套件相近（編輯距離 ≤2）**且**本身看起來新／低訊號（年齡 <30 天，或僅 npm 的週下載量 <100）的比例    |
| 套件成熟度   | 15%  | 資訊性指標：年齡小於 30 天的依賴比例。「新」本身不代表壞，所以這是權重最輕的子分數                                        |

**打字搶注偵測永遠以註冊庫的實際資料為準，不只靠字串相似度。** 一個真
實、歷史悠久、剛好名稱跟熱門套件相近的套件（例如 npm 的 `request`，一個
2011 年就存在的真實套件）絕不會只因為編輯距離命中就被標記——只有「名稱
相近**且**本身又新或下載量低」的套件才會被標記。已用單元測試針對這個
確切案例驗證過。

**已知限制**：

- 「知名套件」清單是每個生態系精選約 60 個名稱的白名單
  （`popular_packages.py`），不是即時的下載量排行榜——搶注一個不在這份
  名單上的熱門名稱不會被抓到。
- **PyPI 套件完全沒有下載量訊號。** pypistats.org（最直覺的資料來源）
  在連續請求下會回 429——已實測驗證，不適合在一次執行裡檢查 N 個依賴。
  這件事會用一則警告揭露在輸出裡，不會被默默當成 0 處理。
- `requirements.txt` 裡的 `-r other.txt` 不會遞迴追蹤。

#### S3 展示

對一個真實健康的 repo（`psf/requests`，`--json` 節錄）：

```
S3 hallucinated dependency: 100/100 [clean]
  dependency existence   100/100  all 12 dependencies exist in their registry
  typosquat risk         100/100  12 existing dependencies checked, no typosquat-like names found
  package maturity       100/100  0/12 dependencies with known age are <30 days old
  manifests: pyproject.toml, requirements-dev.txt
  warning: PyPI packages carry no download-count signal (pypistats API too rate-limited)
```

對一個自製的測試 fixture（3 個真實依賴即時查過 PyPI + 1 個確認不存在的
名稱 + 1 個合成的打字搶注樣式條目——原因見下方「為什麼是合成的」）：

```
overall: 40/100  pattern: hallucinated-dependency  formula: s3.v1
  dependency existence   40/100  1/5 dependencies don't exist in their registry: zzz-repovet-hallucinated-fixture-test-9f3k2
  typosquat risk         25/100  1/4 existing dependencies look like typosquat candidates: reqeusts (close to requests, 3 days old)
  package maturity       75/100  1/4 dependencies with known age are <30 days old
```

_為什麼有一個條目是合成的_：要找到一個「真實存在、新／低下載量、同時
又是正在進行中的打字搶注攻擊」的套件名稱，等於要主動去找出並在公開
demo 裡點名一個真實的攻擊套件——這件事我們不會做。fixture 裡「不存在
套件」的那一半（權重更重、更嚴重的訊號）是 100% 真實的：
`zzz-repovet-hallucinated-fixture-test-9f3k2` 已即時對 PyPI JSON API
驗證過（回傳 HTTP 404）才拿來用。打字搶注的那一半用的是手工建構的
`PackageInfo`、直接餵進 `compute_s3`——評分邏輯本身不在乎資料是不是來
自即時查詢，這裡如實揭露，不假裝是即時發現。

### S4 — AI Slop 特徵提示（v0，`formula "s4.v0"`）

**刻意不做成分數。** 跟 S1/S2/S3 不同，S4 沒有 0-100 數字、也沒有
`pattern` 判定——依照規格，這是工具裡誤判風險最高的訊號（README 模板相
似度、commit 訊息同質性、專案骨架相似度，這些完全合法、真人維護的專案
也都會出現）。v0 只輸出 `signals.s4.hints[]`：每個 hint 是一個觀察 + 一
個原始數字 + 明確的「正常 repo 也會這樣」免責聲明。沒有加總，沒有判
定。S4 屬於新興的「AI-slop linter」工具類別；跟 S1/S3 不同，它不是改
編自某篇特定論文或工具。

| 提示                  | 衡量什麼                                                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| README badge 密度     | README 中 shields.io／badge 樣式圖片的數量                                                                               |
| README emoji 標題密度 | 程式碼區塊外的 `#` 標題中，含 emoji 的比例                                                                               |
| README 罐頭用語命中數 | 命中一份常見「AI 生成 README」慣用語精選清單的次數                                                                       |
| commit 訊息長度均勻度 | 最近 30 筆 commit 訊息長度的變異係數（越低越均勻）；n<8 時跳過                                                           |
| repo 骨架完整度       | 常見專業專案標記存在的數量（LICENSE、CONTRIBUTING.md、CODE_OF_CONDUCT.md、SECURITY.md、issue 模板、`.github/workflows`） |

`--reply` **預設排除 S4**——這個最容易誤判的訊號不該出現在公開貼文裡，除
非使用者主動要求。加上 `--include-s4` 才會在摘要裡多一段「AI-slop 提示
（實驗性）」。

#### S4 展示——誠實結果：這組樣本上幾乎沒有鑑別力

依照規格本身的指示，v0 訊號如果鑑別力接近零，如實回報就是可以接受的結
果——不該挑一個好看的對比組來硬做出比較漂亮的結果。實際跑在一個正常
repo（`psf/requests`）與一個從 S1 校準集裡挑出、疑似 AI-slop 的 repo
（`sidetrip-ai/ici-core`，一個小型「AI 助理」專案）：

| 提示                  | psf/requests（正常） | ici-core（疑似 AI-slop）            | 有鑑別力嗎？                                                             |
| --------------------- | -------------------- | ----------------------------------- | ------------------------------------------------------------------------ |
| README badge 密度     | 5                    | 0                                   | **沒有——方向反了。** Badge 通常代表真的有 CI/PyPI 整合，不是 slop 的訊號 |
| README emoji 標題密度 | 0/4（0%）            | 0/26（0%）                          | 沒有——兩者都是零                                                         |
| README 罐頭用語命中數 | 0/9                  | 1/9（「we welcome contributions」） | 微弱，方向符合預期，但證據薄弱                                           |
| commit 訊息長度均勻度 | CV 0.42              | CV 0.24                             | 微弱到中等，方向符合預期（更均勻）                                       |
| repo 骨架完整度       | 3 個標記             | 3 個標記                            | 沒有——打平                                                               |

**結論**：在這組樣本上，只有一項提示（commit 訊息均勻度）微弱地指向預
期方向；一項（badge 密度）朝**相反**方向（這正是它需要免責聲明的原
因）；其餘完全沒有鑑別力。這跟 repovet 在其他地方一貫的誠實態度一致：
v0 的 AI-slop 提示是給人看一眼參考用的，不是偵測器。沒有為了讓結果好看
而事後調整或替換任何特徵。

這次 demo 過程中發現並修好一個真實 bug，值得記一筆：原本用陽春的
`#` 行數統計標題，會把 ici-core 裡 ` ``` ` 圍起來的安裝範例中的 bash 註
解也算成 markdown 標題，把標題數灌到 60。修法是先排除程式碼區塊內的行
再計數（`ai_slop_hints.py` 的 `_lines_outside_code_fences`），並有一個
回歸測試覆蓋這個案例。

### `--reply`

`repovet gh:owner/repo --reply` 產生一段中立、以證據為主的摘要，可以直
接貼進 GitHub issue、Hacker News 或 Reddit 討論串回答「這個 repo 可信
嗎？」——包含 S1/S2/S3 分數、3-5 個最低分（最影響決策）的子分數作為證
據、一行方法論／限制說明、以及工具署名。絕不使用指控性語言（用「異常
模式」，絕不用「詐騙」／「造假」）——這個紀律已經內建在底層的證據字串
裡；`--reply` 只是組裝既有的內容，不會生成新的論斷。`--reply --lang zh`
會用繁體中文呈現同樣的內容——兩種語言現在都是原生撰寫（見下方 M2.5）。
除非加上 `--include-s4`，否則不含 S4。

#### M2.5：證據現已原生英文化（已解決的範圍缺口）

M0-M2 時所有證據文字都是用中文寫的，導致英文版 `--reply` 會逐句嵌入中
文句子——協調者正確地把這件事標記為公開發文前的硬性阻塞問題。修法：
`scoring.py`/`star_scoring.py`/`dependency_scoring.py`/`ai_slop_hints.py`
裡的每個 `score_*` 函式現在都吃一個 `lang: "en" | "zh"` 參數（預設
`"en"`），兩種語言的字串在**同一個構造點並列撰寫**（不拆到不同檔案），
避免未來只改了事實的一種語言版本、卻悄悄漏掉另一種。`SubScore.name`／
`Hint.name` 與 `pattern` 永遠是英文，不管 `lang` 為何——它們是其他程式
碼與測試用來比對的穩定識別碼，不是要在地化的文案。公式版本沒有升版
（純文字改動，邏輯／權重／門檻都沒動）；所有既有測試維持原樣通過，另外
每個模組加一個新的語言一致性測試（跨語言分數／pattern 相同，只有文字
不同）。

還有一個小的殘留缺口，選擇揭露而不是悄悄放著：S1 最上層描述星標取樣策
略的 `sampling_note` 欄位，不管 `--lang` 為何都還是英文——它是收集器層
級的 metadata 欄位，不是協調者當初要求的那些逐子分數證據字串之一，但
在 `--lang zh` 的輸出裡看起來會有點不一致。這裡沒有修，只是標記出來，
避免看起來像是疏忽。

### 自動化／機器人

repovet 可以用 GitHub Action 執行，取代手動呼叫 CLI，提供兩種刻意設計
成 **opt-in** 的形式——沒有任何路徑會在維護者沒有主動要求的情況下掃描
或留言。

#### 1. `/repovet-check` 留言機器人（本 repo）

在 [`takowei/repovet`](https://github.com/takowei/repovet) 任何 issue 底
下留言 `/repovet-check gh:owner/repo`，機器人就會在同一個 issue 裡回覆
`owner/repo` 的 `--reply` 風格摘要。回覆永遠回到指令被打出的那個
issue——對 `owner/repo` 做檢查，絕不會導致留言被貼到 `owner/repo` 本身。
實作路徑是 `.github/workflows/issue-comment-bot.yml` →
`src/repovet/bot_cli.py` → `src/repovet/bot.py`，使用 Action 內建的
`GITHUB_TOKEN`（範圍只限本 repo——不涉及個人 PAT，你不需要管理任何東
西）。

#### 2. 可重用的觀察清單 workflow（你的 repo，你的 opt-in）

如果你想對自己在意的 repo／依賴做定期 repovet 檢查，把一小段 workflow
複製進**你自己的 repo**，呼叫 `takowei/repovet` 提供的可重用
`workflow_call` workflow，掃描你自己維護的觀察清單檔案。它會照你設定的
排程掃描，並把報告以新 issue 形式貼在**你自己的 repo** 裡——一樣使用你
自己 repo 的 Action-scoped token，永遠不會碰到你清單以外的任何 repo。
完整複製貼上設定：[`docs/reusable-watchlist-workflow.md`](docs/reusable-watchlist-workflow.md)。

#### 為什麼不做「掃到誰就自動留言誰」？

因為那是垃圾留言機器人的行為，會讓你被 rate-limit 或封鎖——GitHub 是唯
一有公認自動留言慣例的平台（類似 Snyk／Socket 的做法），即使在那裡也是
opt-in 專屬。以上兩種機制都只會在維護者自己明確呼叫 repovet 的 repo 內
動作——絕不會動到第三方的 repo。

### GitHub App / Marketplace（第一階段：免費方案上架）

在上面兩種基於 Action 的形式之外，第三種自動化形式：一個自帶 webhook
伺服器、瞄準 GitHub Marketplace 的 **GitHub App**。上面的 Action 機器人
跑在 GitHub 自己的 runner 裡、不需要你維運任何基礎設施；而 Marketplace
的 _App_（相對於 Marketplace 的 _Action_）需要你自己跑一個常駐的
webhook endpoint——GitHub 每個事件都會呼叫它，App 型上架沒有辦法繞過這
一點。

**為什麼要做 App，而不是「就用」上面的 Action 機器人？** Action 也有
Marketplace 上架管道，但付費訂閱的計費機制（`marketplace_purchase`
webhook、每帳號的方案狀態）在 GitHub 的模型裡只接給 App 用——所以第二
階段（付費方案）需要走 App 這條路，而第一階段就先蓋在同一套骨架上、只
是先只開放免費方案。

#### 已實作內容

- `src/repovet/app_server.py`——一個只用標準函式庫（`http.server`，沒有
  用 Flask）的小型 webhook 伺服器。`POST /webhook` 會先驗證
  `X-Hub-Signature-256` 的 HMAC 簽章（`src/repovet/webhook_security.py`，
  任何缺失或無效簽章一律失敗關閉），才會碰內容本身。`GET /health` 供
  存活檢查。
- `src/repovet/app_auth.py`——簽發 App 的 RS256 JWT，並換取每個安裝實例
  的短效 access token（`get_installation_token`）。每次 webhook 送達都
  重新簽發 token，不會跨請求快取。
- `src/repovet/app_webhook.py`——事件分派：
  - `pull_request`（`opened`/`reopened`/`synchronize`）：對 PR 所在的
    repo 跑一次 repovet 掃描，把結果以 PR 留言形式貼出，沿用跟 Action
    機器人相同的 `bot.py`/`reply.py` 渲染路徑。
  - `marketplace_purchase`（`purchased`/`changed`/`pending_change`/
    `cancelled`）：讓 `src/repovet/plan_store.py`（本機 sqlite）與
    GitHub 的計費狀態保持同步。**即使第一階段只出免費方案，這條路徑現
    在就先接好**——因為 GitHub 要求 App 先累積 ≥100 次安裝才能開放付費
    方案，所以在門檻達到前這段邏輯會保持休眠，但程式碼必須先存在。
  - `installation`、`installation_repositories`、`ping`：確認收到，不
    做任何動作。
- `src/repovet/plan_store.py`——`account_login → plan` 的 sqlite 表；
  `get_plan()` 是未來任何功能分級要讀取的唯一入口。

#### 執行伺服器

```bash
REPOVET_APP_ID=... \
REPOVET_APP_PRIVATE_KEY="$(cat app-private-key.pem)" \
REPOVET_WEBHOOK_SECRET=... \
python3 -m repovet.app_server   # 或：repovet-app-server
```

三個機密都只從環境變數讀取——原始碼裡永遠不會寫死檔案路徑，也不會被
記錄下來。`PORT`（預設 `8080`）是它讀取的唯一其他環境變數。

下面手動步驟的確切複製貼上清單（欄位值、權限層級、事件清單）見
`docs/github-app-setup.md`。

#### 手動步驟（GitHub 端，本沙盒無法自動化——由 Root 親自操作）

1. 在 github.com/settings/apps/new 建立 GitHub App：名稱、首頁網址、
   webhook 網址（`https://<your-host>/webhook`）、webhook secret、權限
   （`Pull requests: Read & write`、`Contents: Read`、
   `Metadata: Read`），並訂閱事件 `pull_request`、
   `marketplace_purchase`、`installation`、`installation_repositories`。
2. 產生 App 的私鑰（會下載一個 `.pem`）；把它和 webhook secret 留在
   repo 之外——在伺服器部署的地方設成環境變數／secrets，永遠不要
   commit。
3. 把 `repovet-app-server` 部署到一個有穩定公開 HTTPS 網址的地方（一台
   小型 VPS 後面接反向代理，或任何容器主機）——本 repo 不包含部署／主
   機代管設定，只有伺服器本體。
4. 在 GitHub Marketplace 上架這個 App：Marketplace 開發者協議、logo、
   功能卡片、截圖、上架文案、定價方案頁（第一階段只有免費方案）。
5. 送審（真人審核，沒有公開的 SLA——社群回報約 2-6 週）。
6. 一旦達到 ≥100 次安裝，就可以在 Marketplace 上架頁加上付費方案——
   `plan_store`／`app_webhook.py` 已經處理好對應的 `marketplace_purchase`
   事件，開啟時不需要改任何程式碼。
